## 1. 확정된 결정

### 1.1 Slack 알림과 S3 업로드는 API 서버가 한다

처음 다이어그램에는 탐지 엔진 → Slack 선이 있었으나 API 서버로 옮겼다. 이유:

- **알림 누락 방지**: 해시 블랙리스트/캐시 히트로 차단되는 파일은 탐지 엔진을 거치지 않는다. 탐지 엔진이
  알림을 보내면 가장 흔한 차단 경로(알려진 악성 파일)의 알림이 빠진다.
  ```
  ① 해시로 차단 → 탐지 엔진 안 거침 → (엔진이 알림 담당이면) Slack 알림 없음 ❌
  ② YARA로 차단 → 탐지 엔진 거침   → Slack 알림 있음 ✅
  ```
- **처리 일원화**: 최종 판정이 모이는 API 서버 한 곳에서 판정 이력 저장, SSE(관리 콘솔), Slack을 함께 처리한다.
  ```
  API 서버
   ├─ 해시로 차단 ─┐
   └─ YARA로 차단 ─┴─→ 차단 이벤트
                        ├─ RDS 판정 이력 저장
                        ├─ SSE → 관리 콘솔
                        ├─ S3 격리 파일 업로드
                        └─ Slack 알림
  ```
- **보안 격리**: 탐지 엔진은 공격자가 만든 파일을 파싱하는 가장 위험한 컨테이너다. 파서가 뚫렸을 때
  인터넷 연결, Slack Webhook URL, AWS 권한(IAM 인스턴스 프로파일은 EC2 전체 단위라 컨테이너별로 좁힐 수
  없음)이 없어야 피해가 컨테이너 안에서 끝난다.

### 1.2 탐지 엔진은 API 서버하고만 통신한다 — 네트워크 설정으로 강제

코드상 약속이 아니라 Docker 네트워크로 강제한다.

```yaml
networks:
  engine-net:
    internal: true    # 외부(인터넷, AWS, EC2 메타데이터) 연결 불가

services:
  detection-engine:
    networks: [engine-net]              # 이 네트워크만
  api-server:
    networks: [engine-net, default]     # 엔진 + 외부(RDS/S3/Slack/ElastiCache)
  prometheus:
    networks: [engine-net, default]     # 메트릭 수집용
```

- 예외: Prometheus가 탐지 엔진의 메트릭을 **가져가는(inbound)** 연결은 허용. 탐지 엔진이 먼저 여는
  연결은 없다.
- 추가 권장: 탐지 엔진 컨테이너에 `mem_limit`, `cpus`, `read_only: true`.

### 1.3 인증은 MVP 범위 밖

- MVP에서는 구현하지 않는다.
- 단, `2026-09-13-mvp-scope.md`의 "제외 기능" 목록에는 아직 없으므로 추가 필요 (9장).

## 2. 다이어그램 수정 사항 (2026-09-15 두 번째 버전 기준)

### 이미 반영됨 ✅

- Slack 점선 출발점 → API 서버
- S3 선 출발점 → API 서버(업로드)
- 탐지 엔진은 API 서버와만 연결
- "장애지" 메모 삭제

### 2.1 🔴 최우선: 응답 보류 흐름 표시

**문제**: 지금은 `브라우저 → 가로채기 → 스풀 저장` 방향이라, 파일이 **브라우저에서 나오는** 것처럼 보인다.
즉 "이미 받은 파일을 검사하는 백신"과 구분이 안 되고, 서비스 차별점(디스크에 닿기 전에 막음)이 안 보인다.

**오리진 서버란**: 파일이 원래 있는 웹사이트 서버 (예: 크롬 설치 파일이면 구글 서버, 깃허브 릴리스면 깃허브 서버).

**실제 동작**:
```
① 브라우저: "chrome_installer.exe 주세요"
② 로컬 에이전트(프록시): 요청을 오리진 서버로 전달
③ 오리진 서버: 파일 전송
④ 로컬 에이전트: 파일을 받되 브라우저에는 안 넘기고 붙잡음 (응답 보류)
                 스풀 저장 + SHA-256 → 검사 서버(AWS)에 해시 조회 / (캐시 미스 시) 업로드
⑤ 판정 결과 수신
⑥ 안전 → 붙잡아 둔 응답을 브라우저에 전달 / 악성 → 403 차단 응답
```

**그려야 할 모양**:
```
엔드포인트 PC
┌───────────────────────────────────────────┐
│  브라우저  ◀─ ⑥ 통과 / 403 ──┐            │
│     │ ① 다운로드 요청          │            │
│     ▼                          │            │
│  로컬 에이전트 (프록시) ── 응답 보류 ──┘    │ ── ③ 해시 / ④ 업로드 ──▶ NGINX
│   · 스풀 저장 (UUID.tmp, 0600)             │ ◀─ ⑤ 판정 ───────────
│   · SHA-256 계산                            │
└──────────────┬────────────────────────────┘
               │ ② 응답 수신 (브라우저에 안 넘김)
               ▼
          오리진 서버
```

체크리스트:
- [ ] 엔드포인트 PC 바깥에 **오리진 서버** 박스 추가
- [ ] PC 안에 **로컬 에이전트(프록시)** 박스를 브라우저와 오리진 서버 사이에 두고, 스풀 저장·해시 계산을 그 안에 넣기
- [ ] 판정이 에이전트로 **돌아오는** 방향과 에이전트 → 브라우저 "통과 / 403" 화살표 추가

### 2.2 🟠 라벨 수정

- [ ] API 서버 "해시 조회 — 캐시 미스 시" → 해시 조회는 **항상** 수행. "캐시 미스 시"는 **업로드**의 조건
- [ ] RDS "화이트/블랙리스트" → **"판정 이력 · 화이트/블랙리스트"** (PC 현황 = 최근 차단 이력 조회 기능의 저장소)
- [ ] 업로드 → S3 화살표에 **"악성 판정 시"** 표기 (지금은 미확인 파일 전부가 S3에 쌓이는 것처럼 보임)
- [ ] API 서버 → 탐지 엔진 화살표를 양방향 또는 "판정 요청/결과 (gRPC)"로 표기

### 2.3 🟡 선택 수정

- [ ] Monitoring → Slack 선: Prometheus는 Slack으로 직접 못 보냄 → **Alertmanager** 추가 또는 출발점을 Grafana(Grafana Alerting)로
- [ ] Prometheus → API 서버 / 탐지 엔진 메트릭 수집 점선
- [ ] NGINX 또는 API 서버에 "인증 (에이전트 토큰 / 콘솔 로그인)" 한 줄 — 구현은 안 해도 최종 구조에는 표기 권장
- [ ] Route53(도메인) 추가
- [ ] API 서버 안의 "대시보드" → "통계 API / 이벤트(SSE)"로 이름 변경 (Grafana, 관리 대시보드와 이름 중복)

## 3. 아키텍처 피드백 — 구현 시 주의할 점

### 3.1 인증 (MVP 이후 필수)

- 정책 API·화이트리스트가 인터넷에 열려 있으면 **누구나 악성 해시를 화이트리스트에 넣어 탐지를 우회**할 수 있다.
- 업로드 API가 열려 있으면 서버를 무료 분석기로 쓰거나 DoS 공격이 가능하다.
- 최소 구성: 에이전트 = 기기별 토큰(또는 mTLS), 콘솔 = 로그인(JWT/세션).
- Vercel(콘솔)과 EC2(API)는 도메인이 달라서:
  - CORS 설정 필요
  - SSE의 `EventSource`는 `Authorization` 헤더를 못 붙임 → `SameSite=None` 쿠키 또는 짧게 만료되는 쿼리 토큰
- 발표 예상 질문: "화이트리스트는 누가 바꿀 수 있나요?" — 답변 준비

### 3.2 NGINX gRPC / SSE 설정 함정

| 설정 | 기본값 | 문제 |
|---|---|---|
| `client_max_body_size` | 1MB | gRPC 요청에도 적용 → 큰 파일 업로드 시 413 |
| `grpc_read_timeout` / `grpc_send_timeout` | 60s | 응답 보류 중 판정이 늦으면 먼저 끊김 |
| gRPC 메시지 크기 | 4MB (grpc-java 기본) | 파일은 client-streaming으로 청크 전송 필요 |
| `proxy_buffering` (SSE 경로) | on | 이벤트가 버퍼에 쌓여 실시간으로 안 옴 → `off` |

- EC2의 NGINX가 직접 TLS를 끝내므로 ACM 인증서 사용 불가 → **Let's Encrypt** 필요.
  Vercel(HTTPS)에서 호출하려면 EC2 쪽에도 도메인 + 유효한 인증서 필수.

### 3.3 모니터링

- Prometheus/Grafana가 감시 대상과 같은 EC2 → **EC2가 죽으면 알림도 같이 죽음**.
- 서버 생존 확인은 외부에서: Route53 Health Check 또는 CloudWatch 알람.

### 3.4 기타

- **오탐 복원 시 캐시 무효화**: Redis 평판 캐시에 "악성"이 남아 있으면 복원해도 계속 차단된다. 블룸 필터는
  삭제가 불가하므로 화이트리스트를 별도 레이어로 두고 조회 순서에서 먼저 확인한다.
- **"PC 현황" 기능**: 여러 PC를 구분하려면 에이전트 등록 / 기기 ID / 하트비트가 필요한데 아직 어느 설계 문서에도 없다.
- **EC2에서 직접 `docker compose build`**: 빌드 중 CPU 점유 + 재기동 동안 모든 에이전트가 **다운로드를
  차단**함 (fail-close 고정, 2026-09-18 결정) → 데모 직전 배포 금지. 재기동 시간이 곧 전면 다운로드
  중단 시간이다.
- **메모리**: Spring Boot + 탐지 엔진 + Prometheus + Grafana + NGINX를 한 대에 올리면 최소 4GB 권장.

**결론**
- 다이어그램의 "에이전트가 브라우저와 오리진 사이에서 가로챈다"는 구조를 뒷받침하는 근거는 **Python(mitmproxy) PoC**다.
- Java PoC는 "Spring/Reactor로 응답 보류 로직을 논블로킹으로 짤 수 있다"를 증명했다. 이 지식은 API 서버의
  비동기 처리(gRPC 대기, SSE)에 재사용 가능.
- Spring Cloud Gateway는 라우트 기반이라 포워드 프록시 요청(`GET http://다른사이트/파일`, HTTPS용 `CONNECT`)을
  기본으로 처리하지 못한다. 에이전트를 Java로 만들려면 Netty로 포워드 프록시 + TLS 인터셉션을 직접 구현해야 한다.

## 5. 기술 선택 (제안 — 팀 합의 필요)

```
로컬 에이전트   → Python (mitmproxy addon)
API 서버        → Spring Boot (Java)
탐지 엔진       → Python (5주 전체 기능 기준)
관리 콘솔       → React (Vercel)
에이전트 ↔ API 서버 ↔ 탐지 엔진 = gRPC → 언어가 달라도 문제없음
```

### 5.1 로컬 에이전트: Python + mitmproxy

| 에이전트에 필요한 것 | Python (mitmproxy) | Java |
|---|---|---|
| 포워드 프록시 | ✅ 기본 기능, 브라우저 실측 완료 | ❌ 직접 구현 |
| `CONNECT` (HTTPS 연결) | ✅ 내장 | ❌ Netty로 직접 구현 |
| TLS 인터셉션 (CA, 사이트별 인증서 생성) | ✅ 내장 | ❌ 직접 구현 (2주 이상, 고위험) |
| 응답 보류 / 403 교체 | ✅ 검증됨 | ✅ 검증됨 |

알고 있어야 할 점:
1. **대용량 파일**: mitmproxy는 기본적으로 응답 전체를 메모리에 올린 뒤 훅을 호출한다. 스트리밍 모드
   (`flow.response.stream`)를 켜면 헤더가 먼저 나갈 수 있어 403 교체가 불가능해질 수 있다(확인 필요)
   → **"N MB 초과 파일 정책"(통과 / 차단 / 경고)을 정해야 한다.**
2. **발표 예상 질문 "mitmproxy 붙인 거 아니냐"**: 답변 — "프록시·TLS는 검증된 도구에 맡기고, 우리가 만든
   것은 다운로드 판별 → 응답 보류 → 스풀·해시 → 서버 판정 → 차단 파이프라인이다."
3. **사용자 PC 배포**: 실제 배포 시 PyInstaller 등 패키징 필요 (에이전트 배포는 현재 설계 범위 밖).

### 5.2 탐지 엔진: 기간에 따라 다름

**4일 MVP (YARA 매칭만)**: 어느 쪽이든 가능.
- Python: `yara-python` 한 줄, PoC 3가 이미 Python으로 설계됨.
- Spring: 팀 주력 스택. 단 YARA는 JNI가 아니라 **`yara` CLI 서브프로세스**로 호출할 것 — YARA 본체는 C라서
  JNI로 JVM 안에서 부르다 크래시하면 JVM 전체가 죽고 검사 중이던 다른 요청도 모두 실패한다.

**5주 전체 기능 (매직바이트 → PE 파싱 → 엔트로피 → YARA + 프로세스 격리·리소스 상한)**: **Python 추천**.
- 제품 설계 문서 7장 "파싱은 별도 프로세스, 메모리·CPU·시간 상한, 크래시 시 해당 파일만 실패" 요구가 실제로 들어온다.
- Python: `ProcessPoolExecutor`/워커 프로세스 + `setrlimit` + 타임아웃으로 모든 파싱을 싸게 격리.
  도구 생태계가 표준 (`python-magic`, `pefile`, `yara-python`).
- Java: 파일마다 JVM을 띄우기엔 무거움 → [PortEx](https://github.com/struppigel/PortEx)(PE 분석)는 JVM 안에서
  격리 없이 돌리고 YARA만 CLI로 분리하는 절충이 된다. 조작된 PE 하나가 메모리를 폭주시키면 다른 요청까지 같이 죽음.
- Java 참고: YARA 공식 Java 바인딩은 없음. 비공식 JNI 바인딩 [subreption/yara-java](https://github.com/subreption/yara-java)
  (원본 [p8a/yara-java](https://github.com/p8a/yara-java)는 관리 중단). YARA-X 공식 바인딩은 Python/Go/C만 제공
  ([YARA-X Python API](https://virustotal.github.io/yara-x/docs/api/python/)).
- 팀에 Python을 다룰 사람이 없을 때만 Spring + PortEx + YARA CLI.

### 5.3 블룸 필터: Redis 비트맵으로 직접 구현

- `SETBIT`/`GETBIT`로 구현하면 ElastiCache의 Redis 모듈 지원 여부에 좌우되지 않는다.
- 제품 설계 문서 Phase 3 "m·k 파라미터 직접 산출" 목표와도 맞는다.

## 6. 5주 일정 (제안)

원칙:
1. **1주차에 끝까지 이어지는 뼈대**(기능은 얕아도 전체 흐름이 도는 상태)를 먼저 만든다.
2. **인터페이스 계약(gRPC proto, REST API)을 먼저 확정**해서 트랙별 동시 진행이 가능하게 한다.
3. 인프라(EC2·NGINX·도메인)는 5주차가 아니라 **1~2주차**에 올려 환경 문제를 일찍 드러낸다.

트랙 4개 동시 진행 가정. 인원이 적으면 에이전트 + 탐지 엔진(둘 다 Python)을 한 사람이 맡는 식으로 합친다.

| 주차 | 에이전트 (Python) | API 서버 (Spring) | 탐지 엔진 (Python) | 콘솔 (React) / 인프라 |
|---|---|---|---|---|
| **1** | **proto·API 계약 확정** / HTTPS 인터셉션 실측 | 해시 조회·판정 API | YARA 워커 | EC2·NGINX·도메인·TLS 인증서 |
| | ★ **끝까지 연결: 다운로드 → 해시 → YARA → 통과/403 (HTTPS 포함)** | | | |
| **2** | 다운로드 판별 / 스풀 보호 규칙 (UUID.tmp, 0600, XOR, 인덱싱 제외) / 스트리밍 해시·업로드 | RDS 스키마(판정 이력·리스트) / S3 격리 업로드 / 블룸 필터(비트맵) | 매직바이트 → PE 파싱 / 섹션 엔트로피 | CI/CD(SSH 배포) / NGINX gRPC 대용량 설정 |
| **3** | 대용량 파일 정책 / 정책 수신(바이패스 도메인) | 화이트리스트 레이어 / Slack 알림 / SSE 이벤트 | 워커 격리·리소스 상한 | 콘솔 뼈대 + 인증 |
| **4** | (선택) 서킷 브레이커 + 로컬 캐시 | 정책 API / 오탐 복원 / Redis 캐시 무효화 | 룰 확장·오탐 튜닝 | 이벤트 스트림 / 정책 편집 / 격리 파일 관리 / 대시보드 |
| **5** | **주 초 기능 동결** → 성능 측정 (오버헤드·p99·캐시 히트율·메모리·전송량 절감률) / Prometheus·Grafana / 버그 수정 / 데모 리허설 / 발표 자료 | | | |

### 1주차에 반드시 없애야 할 위험 3가지

늦게 발견하면 설계를 다시 해야 하는 항목이다.

1. **mitmproxy HTTPS 인터셉션** — macOS/Windows에서 CA 등록 후 실제 HTTPS 다운로드를 붙잡을 수 있는지. 아직 한 번도 성공하지 못함.
2. **mitmproxy 대용량 파일** — 스트리밍 모드에서 헤더가 언제 나가는지 → "N MB 초과 파일 정책" 결정.
3. **NGINX 경유 gRPC 파일 업로드** — `client_max_body_size`, 타임아웃, 청크 스트리밍이 실제로 통과하는지.

## 7. 5주여도 하지 않을 것

- TLS 인터셉션 직접 구현 (mitmproxy 사용)
- 메시지 브로커, 다중 인스턴스/오토스케일링 ([`2026-09-12-detection-engine-broker-decision.md`](2026-09-12-detection-engine-broker-decision.md) 기준 유지)
- 외부 위협 인텔리전스(VirusTotal/NVD·CVE) 연동 (2026-09-15 회의로 전체 범위 제외)
- 서킷 브레이커 + 로컬 SQLite 캐시는 팀이 초기 단계에서 빼기로 결정 → 4주차에 여유가 있을 때만

|---|---|
| 이미 받은 파일을 검사하는 백신과 뭐가 다른가? | 응답 보류 — 브라우저에 바이트가 닿기 전에 판정 (2.1 흐름도) |

| 이 중 실제로 동작하는 것은? | MVP/5주 범위 중 구현된 항목 구분해서 답변 |
