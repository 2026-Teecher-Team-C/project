# 팀원에게 공유해야 할 아키텍처 결정 사항

- 날짜: 2026-09-12
- 목적: 상대방(아키텍처 이미지 제안자)이 그린 방향과 다르게, **우리 쪽 판단으로 결정한 항목**만
  추적한다. 상대방 제안을 그대로 채택했거나, 상대방이 명시하지 않은 빈 부분을 우리가 채운 경우는
  상대방 제안과 충돌이 없으므로 이 목록에 넣지 않는다.
- 사용법: 새로운 결정을 내릴 때마다, 그 결정이 상대방이 그린 그림/제안의 방향과 실질적으로
  다르면 이 문서에 항목을 추가한다. 전달 완료 후 상태를 체크한다.

## 전달 필요 목록

### 1. API 서버 ↔ 탐지 엔진 통신: 메시지 브로커 미도입

- **상대방 제안(이미지)**: 탐지 엔진을 API 서버와 별도 Docker 컨테이너로 분리해서 그림 — 비동기/
  메시지 브로커 구조를 암시하는 형태
- **우리 결정**: 동기 gRPC 호출 + API 서버 측 세마포어(동시 처리 수 제한)로 유지. 메시지 브로커
  도입 안 함
- **이유**: 에이전트가 판정 날 때까지 HTTP 응답을 보류해야 하는 제약 때문에 파이프라인 전체가
  사실상 끝까지 동기적으로 기다려야 함. 브로커를 넣으면 오히려 reply 대기 로직을 새로 만들어야
  해서 복잡도만 늘어남. 현재 EC2 단일 인스턴스 규모에서는 브로커가 필요해지는 조건(다중 워커
  스케일 아웃, 워커 크래시 시 요청 유실 방지, 세마포어로 못 감당하는 유입 속도, 완전
  fire-and-forget 요구사항)에 해당하지 않음
- **상세 문서**: [`2026-09-12-detection-engine-broker-decision.md`](2026-09-12-detection-engine-broker-decision.md)
- **전달 상태**: [ ] 미전달

### 2. RDS: 판정 이력 저장 역할 유지

- **상대방 제안(이미지)**: RDS를 PostgreSQL로, 역할은 "화이트/블랙리스트"로만 표기 — 판정 이력
  저장소가 다이어그램에서 빠져 있음
- **우리 결정**: RDB 종류(PostgreSQL)는 상대 제안대로 채택하되, **판정 이력 저장 역할은 그대로
  유지**해서 같은 RDS에 추가한다 (화이트/블랙리스트 + 판정 이력 두 역할을 함께 담당)
- **이유**: 원래 제품 설계 문서(`프록시-악성코드-탐지-플랫폼.md`)에 "판정 결과 캐싱 및 이력 저장"이
  요구사항으로 명시돼 있고, 관리 콘솔의 위협 통계 대시보드·오탐 복원 이력 조회 기능이 이 저장소
  없이는 동작할 수 없음. 상대방 다이어그램에서 누락된 것으로 판단해 보완함
- **전달 상태**: [ ] 미전달

### 3. 외부 위협 인텔리전스(VirusTotal/NVD·CVE) 장애 시 fail-open 정책 추가

- **상대방 제안(이미지)**: 탐지 엔진이 VirusTotal API, NVD/CVE 피드와 교차조회하는 것만 표시,
  해당 외부 API가 느려지거나 실패했을 때의 동작은 명시 없음
- **우리 결정**: 로컬 검사 서버 장애 정책(서킷 브레이커 + 로컬 캐시 폴백)과 같은 원칙으로
  **fail-open** 채택 — 외부 조회가 타임아웃되면 로컬 YARA/PE 분석 결과만으로 판정하고, 외부
  조회는 판정을 막는 필수 의존성이 아니라 사후 보강 신호로 취급
- **이유**: 외부 서비스(특히 무료 API)는 rate limit·지연이 흔한데, 이게 판정 자체를 블로킹하면
  "응답 보류" 설계 원칙상 사용자 다운로드가 외부 서비스 장애에 볼모로 잡힘. 로컬 탐지 결과만으로도
  1차 판정이 가능하므로 외부 연동은 보강용으로 격하하는 게 안전

## 전달 불필요 (참고용, 충돌 없음)

- **배포 방식 → Docker + SSH 직접 배포**: 상대방 이미지도 Docker였고, 이미지 배포 방식
  (레지스트리 경유 vs SSH 직접)은 이미지에 표시되지 않았던 부분을 우리가 채운 것이라 상대방
  제안과 충돌 없음
- **Redis → Amazon ElastiCache, 관리 콘솔 → Vercel, 모니터링(Prometheus+Grafana), Slack 알림,
  격리 파일 S3 암호화**: 전부 상대방 제안을 그대로 채택
- **에이전트=gRPC, 관리 콘솔=REST+SSE로 프로토콜 분리**: 상대방 제안(gRPC)을 에이전트 채널에
  그대로 적용하고, 관리 콘솔은 원래도 별도 채널이라 프로토콜을 통일할 필요가 없었던 것 — 상대방
  제안과 충돌 아님 (브라우저 gRPC 제약 때문에 REST 유지가 오히려 자연스러운 선택)
