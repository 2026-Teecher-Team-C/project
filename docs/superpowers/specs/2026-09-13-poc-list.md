## cherry-pick 기준

MVP 기능(A~G) 중 "안 될 게 없는" 표준 구현(A/D/F/G)은 제외하고, **"진짜 되는지 모르는" 항목만**
PoC 대상으로 뽑았다.

| MVP 기능 | PoC 대상 여부 |
|---|---|
| B. 응답 보류 | ✅ PoC 1 |

## PoC 1 — 응답 보류(response holding) [MVP 기능 B]

- **검증 대상**: 다운로드 응답 헤더가 브라우저로 전송되기 전에 붙잡아뒀다가, 판정 완료 후
  그대로 흘려보내거나 403으로 막을 수 있는지
- **왜 필요한가**: 시스템 전체 설계가 "헤더 전송 전에는 응답을 막을 수 있다"는 전제 위에
  서 있음. 이 전제가 코드로 검증된 적이 없고, 실패하면 나머지 일정 전체를 재검토해야 하는
  게이트 항목
- **확인할 것**: mitmproxy류 프록시로 실제 헤더 전송 타이밍 제어가 가능한지, 브라우저
  타임아웃 안에 들어오는지
- **일정**: 1일차
- **macOS 개발 환경 노트**: mitmproxy는 크로스플랫폼이라 macOS에서도 PoC 진행 가능. 단,
  (1) HTTPS 인터셉션을 위해 mitmproxy CA를 macOS 키체인에 "항상 신뢰"로 추가해야 함(관리자
  암호 1회 필요), (2) Chrome이 일부 CDN에서 QUIC(UDP)로 다운로드하면 TCP 기반 프록시를
  건너뛰므로 데모용 테스트 파일은 QUIC 안 쓰는 일반 HTTP/1.1 URL로 준비할 것 (QUIC/HTTP3는
  설계 문서상 이미 out of scope). 443 같은 저포트 바인딩이 필요 없는 explicit proxy
  모드(8080 등)를 쓰면 root 권한 문제도 없음
- **구현 방법**:
  1. `pip install mitmproxy`
  2. addon 스크립트 작성 — mitmproxy는 `response` 훅이 서버로부터 전체 응답을 받은 *후*,
     클라이언트로 전달하기 *전*에 호출되므로 이 안에서 붙잡아두면 됨:
     ```python
     # hold_response.py
     import time
     from mitmproxy import http

     BLOCK = False  # 데모용 토글 — 나중엔 판정 로직 결과로 교체

     def response(flow: http.HTTPFlow):
         time.sleep(3)  # 판정 대기 시간 시뮬레이션 (실제로는 해싱+서버조회 자리)
         if BLOCK:
             flow.response = http.Response.make(
                 403, b"Blocked by malware detection platform", {"Content-Type": "text/plain"}
             )
         # else: 아무것도 안 하면 원본 응답이 그대로 클라이언트로 전달됨
     ```
  3. `flow.response.stream`을 기본값(`False`)으로 두면 mitmproxy가 응답 바디 전체를 버퍼링해
     `response` 훅에 넘겨주므로, 이 시점에 전체 파일 바이트에 접근 가능 (PoC 2의 해싱도 여기서
     같이 할 수 있음)
  4. 실행: `mitmdump -s hold_response.py -p 8080`
  5. macOS 시스템 프록시를 `localhost:8080`으로 설정 + mitmproxy CA 키체인 신뢰(위 노트 참고)
  6. 브라우저로 테스트 파일 다운로드 → 3초 지연 후 통과/차단이 `BLOCK` 값에 따라 갈리는지 확인

## PoC 2 — 스트리밍 SHA-256 + 스풀링 단일 패스 [MVP 기능 C]

- **검증 대상**: 파일을 디스크에 스풀하면서 동시에 SHA-256을 계산하는 단일 패스 처리가
  대용량 파일에서도 PoC 1(응답 보류) 위에서 지연 없이 되는지
- **왜 필요한가**: "파일을 두 번 안 읽는다"는 전제가 실제 성능으로 이어지는지, 응답 보류
  시간이 브라우저 타임아웃을 넘기지 않는지 확인 필요
- **확인할 것**: 대용량 샘플 파일 기준 처리 시간, 브라우저 타임아웃 대비 여유
- **일정**: 2일차 (PoC 1 위에 이어서)
- **구현 방법**:
  - **독립 실행 버전** (프록시 없이 순수 성능 측정): 청크 단위로 읽으면서 그 자리에서 해시를
    갱신하고 동시에 스풀 파일에 씀 — 두 번 읽지 않는 단일 패스
    ```python
    import hashlib, os, time

    def spool_and_hash(src_path: str, spool_path: str, chunk_size=64 * 1024) -> str:
        digest = hashlib.sha256()
        fd = os.open(spool_path, os.O_CREAT | os.O_WRONLY | os.O_TRUNC, 0o600)  # 생성 시점에 0600 권한 적용
        try:
            with open(src_path, "rb") as src, os.fdopen(fd, "wb") as dst:
                while chunk := src.read(chunk_size):
                    digest.update(chunk)
                    dst.write(chunk)
        finally:
            pass
        return digest.hexdigest()

    # 측정: 100MB/500MB 테스트 파일(`mkfile -n 500m test.bin` 등으로 생성)로 시간 재기
    start = time.perf_counter()
    h = spool_and_hash("test.bin", "/tmp/spool/uuid.tmp")
    print(time.perf_counter() - start, h)
    ```
  - **PoC 1과 통합할 때**: mitmproxy `response` 훅에서 `flow.response.content`가 이미 전체
    바이트를 들고 있으므로, 그 바이트를 위 `spool_and_hash`와 같은 방식으로 청크 순회하며
    해싱+스풀에 사용하면 됨 (네트워크 수신은 mitmproxy가 이미 버퍼링했으므로, 이 단계는
    "메모리→디스크" 단일 패스를 검증하는 것)
  - 브라우저 타임아웃(보통 수십 초~분 단위) 대비 처리 시간이 여유 있는지 로그로 확인

## PoC 3 — 서버 판정: 해시 대조 + YARA 매칭 [MVP 기능 E]

- **검증 대상**: EICAR 테스트 파일/실제 YARA 룰로 서버가 실제 악성/안전 판정을 내릴 수 있는지
  (라이브러리 연동 자체가 처음이라 검증 필요)
- **왜 필요한가**: 데모의 핵심 장면("악성 파일 차단")이 실제로 동작하는지 보장
- **확인할 것**: YARA 매칭 결과가 기대한 대로 나오는지, 판정까지 걸리는 시간
- **일정**: 3일차, 이후 D/F/G(에이전트-서버 통신, 릴리스/차단 처리, 최소 이력 저장)를 붙여서
  end-to-end 연결
- **구현 방법**:
  1. `pip install yara-python`
  2. 최소 YARA 룰 작성 (EICAR 테스트 문자열 탐지 예시):
     ```yara
     rule EICAR_Test_File
     {
         strings:
             $eicar = "X5O!P%@AP[4\\PZX54(P^)7CC)7}$EICAR-STANDARD-ANTIVIRUS-TEST-FILE!$H+H*"
         condition:
             $eicar
     }
     ```
  3. 안전 파일 판정을 위해 해시 블랙리스트를 먼저 확인 (dict/JSON으로 시작, 나중에 DB로 대체):
     ```python
     import yara

     KNOWN_BAD_HASHES = {"<eicar sha256>"}  # 알려진 악성 해시
     rules = yara.compile(filepath="eicar.yar")

     def judge(file_bytes: bytes, file_hash: str) -> str:
         if file_hash in KNOWN_BAD_HASHES:
             return "malicious"
         if rules.match(data=file_bytes):
             return "malicious"
         return "safe"
     ```
  4. 테스트 데이터: [eicar.org](https://www.eicar.org/download-anti-malware-testfile/) 표준
     EICAR 테스트 파일(안전하게 설계된 68바이트 문자열, 실제 악성코드 아님) + 일반 텍스트/PDF
     파일 하나를 안전 케이스로 사용
  5. 두 파일 각각 `judge()`에 넣어 기대한 판정(`malicious`/`safe`)이 나오는지, 판정까지
     걸리는 시간이 어느 정도인지 확인
  6. **end-to-end 연결 시**: PoC 1의 `response` 훅에서 PoC 2로 해싱한 뒤, 그 바이트+해시를
     `judge()`에 넘겨서 `BLOCK` 플래그를 실제 판정 결과로 교체

## 진행 순서

1일차 PoC 1 → 2일차 PoC 2(1 위에 이어서) → 3일차 PoC 3 + end-to-end 연결 → 4일차 통합 및 버퍼.
PoC 1이 실패하면 전체 일정을 재검토해야 하는 게이트이므로 최우선.
