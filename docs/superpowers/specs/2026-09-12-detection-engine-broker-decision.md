# 탐지 엔진 통신 방식: 메시지 브로커 도입 기준

- 날짜: 2026-09-12
- 관련 문서: [`2026-09-12-deployment-architecture-design.md`](2026-09-12-deployment-architecture-design.md)
- 결론(현재): API 서버 ↔ 탐지 엔진은 **동기 gRPC 호출 + API 서버 측 세마포어(동시 처리 수 제한)**로 유지한다.
  메시지 브로커(RabbitMQ/Kafka/SQS/Redis Streams 등)는 도입하지 않는다.

## 왜 지금은 필요 없는가

이 시스템은 에이전트가 **판정이 날 때까지 브라우저 HTTP 응답을 보류**해야 한다는 제약이 있다
(제품 설계 문서 "응답 보류" 원칙). 즉 API 서버 → 탐지 엔진 구간을 완전 비동기(fire-and-forget)로
바꿔도, 결국 API 서버는 탐지 결과가 나올 때까지 어떤 형태로든 "기다려야" 한다.

브로커를 넣으면 이 "기다림"을 다시 구현해야 한다 — 예: 요청을 큐에 넣고, correlation ID로 reply
큐를 폴링하거나 완료 신호를 대기하는 로직. 이건 순수 gRPC 요청-응답 호출보다 오히려 코드가 늘어나고
장애 지점(브로커 자체의 가용성)이 하나 더 생긴다. 프로세스 격리(크래시 격리, 리소스 상한)는 동기
gRPC 호출만으로도 이미 달성되므로, 지금 규모(EC2 단일 인스턴스)에서 브로커는 과한 인프라다.

## 브로커 도입이 정당화되는 조건

아래 조건 중 하나라도 실제로 발생하면 그때 도입을 검토한다. 지금은 셋 다 해당 사항 없음.

| 조건 | 설명 | 신호 |
|---|---|---|
| 탐지 엔진 다중 워커 스케일 아웃 | 탐지 엔진 처리량이 병목이 되어 여러 인스턴스/워커로 늘려야 함 | 탐지 큐 대기 시간이 지속적으로 증가, 세마포어 대기가 상시 포화 |
| 워커 크래시 시 요청 유실 방지 | 탐지 엔진이 파싱 중 크래시해도 대기 중이던 다른 요청이 유실되면 안 됨 | 탐지 엔진 재시작 빈도가 높아지고, 재시작 시 진행 중 요청이 실패로 이어짐 |
| 유입 속도 > 처리 속도 (자연 백프레셔 필요) | 순간적으로 몰리는 다운로드 요청이 세마포어 제한만으로는 감당 안 됨 | 세마포어 대기열이 무한정 쌓이며 API 서버 메모리/타임아웃 문제 발생 |
| 진짜 비동기(fire-and-forget) 요구사항 등장 | "일단 통과시키고 사후에 격리/알림만" 하는 완전 비동기 모드가 신규로 필요해짐 | 현재 설계엔 없는 시나리오. 예: 저위험 파일 타입은 응답 보류 없이 통과시키고 백그라운드로만 검사 |

## 도입 시 구조 변화 (참고용, 지금 적용 안 함)

- 브로커 자체가 인프라 구성요소로 추가된다 (관리형 서비스 우선 고려: Redis Streams가 이미 있는
  ElastiCache를 재사용할 수 있어 가장 가볍고, RabbitMQ/Kafka는 별도 운영 부담이 커진다).
- "탐지 엔진" 컨테이너는 그대로 두되, 입력 방식만 "gRPC 요청 수신"에서 "큐 컨슈머(구독)"로 바뀐다 —
  별도 EC2 인스턴스 분리는 이 시점에도 필수는 아니다.
- 별도 EC2/오토스케일링으로 완전히 분리하는 것은 **탐지 엔진을 API 서버와 독립적으로 스케일링**하고
  싶을 때만 추가로 필요한 선택 사항이며, 브로커 도입 자체가 이를 강제하지 않는다.
- 응답 보류 제약은 여전히 유지해야 하므로, 브로커를 넣더라도 API 서버는 correlation ID 기반으로
  reply 큐를 기다리거나, Redis pub/sub으로 완료 신호를 기다리는 방식으로 "동기처럼 보이는" 흐름을
  다시 구현해야 한다.
