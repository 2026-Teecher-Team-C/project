## 0. 한 줄 요약

> 브라우저는 **전 과정 동안 응답을 기다리고 있다.** 그래서 모든 단계가 "싼 조회부터 비싼 검사까지"
> 순서로 배치돼 있고, 대부분의 다운로드는 앞쪽 단계에서 끝난다.

### 0.1 "조회"와 "검사"를 같은 말로 부르지 말 것

흐름에 판단 단계가 두 번 나오는데 성격이 완전히 다르다. 팀에서 둘을 같은 말로 부르면 대화가 계속
엉킨다.

| 용어 | 무엇을 하나 | 단계 | 비용 | 위험 |
|---|---|---|---|---|
| **조회** | 해시로 물어보기 | ①~④ | 싸다 (Redis/RDS 한 번) | 없음 |
| **검사** | 원본 바이트를 뜯어보기 | ⑤~⑥ | 비싸다 (업로드 + 파싱) | **파서 취약점 노출** (11장) |

## 1. 전체 그림

```
[사용자 PC]                                    [AWS EC2]

브라우저
  │ ① 다운로드 요청
  ▼
로컬 에이전트 (프록시)  ──────② 요청 전달──────▶  오리진 서버
  │                     ◀─────③ 응답 수신───────
  │
  │ ④ 브라우저에 안 넘기고 붙잡음 (응답 보류)
  │    스풀 저장 + SHA-256 계산
  │
  ├──────⑤ 해시 조회 (gRPC)──────────────────▶  API 서버
  │                                              │  조회 사슬 ①~④ (2장)
  │      ◀──────⑥ upload_needed? ──────────────  │
  │                                              │
  ├──────⑦ 파일 업로드 (캐시 미스일 때만)─────▶  │
  │                                              ├──▶ 탐지 엔진 (YARA/PE)
  │      ◀──────⑧ 판정 수신 ────────────────────┤
  │                                              ├──▶ RDS (판정 이력·캐시)
  │                                              ├──▶ S3 ★악성 판정 시에만
  │                                              └──▶ Slack / SSE (알림)
  ▼
⑨ 안전 → 보류 해제 (브라우저가 그때부터 저장)
   악성 → 403 차단 응답
```

**핵심 제약**: ④의 보류는 **응답 헤더가 브라우저로 나가기 전에** 일어나야 한다. 헤더가 나가면 차단
응답을 만들 수 없다 (제품 설계 6장).

## 2. 조회 사슬 — 걸리면 즉시 종료

API 서버가 해시를 받고 하는 일이다. 위에서부터 순서대로, 걸리면 그 자리에서 끝난다.

| 순서 | 조회 대상 | 저장소 | 히트하면 |
|---|---|---|---|
| ① | `hash_whitelist` | RDS/Redis | 즉시 통과. 검사 안 함 |
| ② | `hash_blacklist` | Redis | 즉시 차단 |
| ③ | 블룸 필터 | Redis 비트맵 | "없음" 확답 → 미확인 파일, ⑤로 |
| ④ | `file_verdicts` | RDS | `NOT is_stale`이면 캐시된 판정 적용 |
| ⑤ | 탐지 엔진 호출 | gRPC | 캐시 미스일 때만 |

### 왜 이 순서인가

**①이 가장 먼저인 이유** — 블룸 필터는 **삭제가 불가능하다.** 오탐으로 복원한 해시는 필터가 계속
"악성일 수도"라고 답하므로, 앞단에서 가로채는 수밖에 없다 (제품 설계 6장).

**③의 답을 해석하는 법** — 블룸 필터는 위양성만 있고 위음성이 없다. 즉 **"없음"은 확답이고
"있음"은 추측**이다. 그래서 "있을 수도"가 나오면 ④에서 정확히 확인해야 한다.

**②④에서 끝나면 파일 업로드가 아예 없다.** 이게 대역폭 2배 소모를 막는 3단 파이프라인의 실체다
(제품 설계 6장 "로컬/서버 경계 설계").

### 왜 ⑤에서 원본이 필요한가 — 해시는 해석할 수 없다

해시는 **일방향**이다. 500MB 파일도 SHA-256은 32바이트이므로 정보가 버려진 것이고 되돌릴 수 없다.
해시로 알 수 있는 것은 단 하나다:

```
해시 → "전에 본 그 파일과 똑같은가?" → 예 / 아니오
```

파일 종류도, 안에 든 코드도, 악성 여부도 해시로는 알 수 없다. 지문으로 "전에 체포된 그 사람인가"는
알 수 있지만 "이 사람이 범죄자인가"는 알 수 없는 것과 같다 — 전과 기록이 있어야 한다.

- `hash_blacklist` / `file_verdicts` = **전과 기록부**
- 해시 = 기록부를 찾는 **조회 키**

기록에 없는 파일은 **원본 바이트를 보는 것 말고는 판단할 방법이 없다.** 그래서 ⑤ 업로드가 존재한다.

### 캐시의 효과는 두 가지다

| 효과 | 내용 |
|---|---|
| 대역폭 | 아는 파일은 업로드하지 않음 |
| **보안** | **아는 파일은 파싱도 하지 않음 → 파서를 노출시키는 횟수 자체가 줄어듦** |

두 번째는 제품 설계 문서에 명시돼 있지 않으나 발표에서 쓸 수 있는 논거다.

## 3. 에이전트 ↔ 서버 경계

### 에이전트는 DB 스키마를 모른다

에이전트가 보내는 것은 gRPC 메시지일 뿐이고, 어느 테이블에 어떻게 넣을지는 **API 서버가 혼자
정한다.** 이유:

- 에이전트는 사용자 PC에 있어 **업데이트가 가장 어려운 컴포넌트**다 (배포 파이프라인도 없다 —
  배포 문서 4장). 스키마가 바뀔 때마다 전 PC를 재배포해야 한다면 컬럼 추가가 불가능해진다.
- 에이전트가 보낸 값을 그대로 INSERT하면 **에이전트를 신뢰하는 것**이 된다. 사용자 PC에서 도는
  프로세스라 조작 가능하다.

### 에이전트가 보내는 것 — 6개 + 경과시간

```protobuf
message InspectRequest {
  string          sha256                = 1;
  string          url                   = 2;
  optional string filename              = 3;
  optional string mime_type             = 4;
  optional string content_disposition   = 5;
  optional int64  file_size             = 6;   // chunked면 없음
  int32           spool_hash_elapsed_ms = 7;   // 시각이 아니라 경과 시간
  // agent_id 없음     — 인증 토큰에서 서버가 도출
  // request_host 없음 — url에서 서버가 파싱
}

message InspectResponse {
  Verdict verdict       = 1;
  Action  action        = 2;   // RELEASE / BLOCK
  bool    upload_needed = 3;
}
```

### 보내지 않는 것과 그 이유

| 컬럼 | 누가 채우나 | 왜 |
|---|---|---|
| `agent_id` | **인증 토큰에서 도출** | 요청에 담으면 남의 `agent_id`를 적어 보낼 수 있다. proto에 필드를 두지 말 것 |
| `request_host` | 서버가 `url`에서 파싱 | 둘 다 받으면 어긋날 수 있다. `url`은 `evil.com`인데 host는 `google.com`이라고 보내면 바이패스 도메인 검사를 우회당한다 |
| `bytes_uploaded` | 서버가 실제 수신량 측정 | 에이전트의 "얼마 보냈다"는 주장을 믿을 이유가 없다 |
| `held_at` `decided_at` | 서버 시계 | 사용자 PC 시계가 틀어져 있을 수 있다 |
| `event_id` | 서버 발급 | |
| `pipeline_status` `decision` `decision_source` `cache_hit` | 서버가 판정하며 결정 | |

### 시각이 아니라 경과 시간을 보내는 이유

보류 시간은 이렇게 쪼개진다:

```
[에이전트] 보류 시작 → 스풀 + 해시 ──┐ ← 이 구간만 에이전트가 안다
[네트워크] gRPC 요청 ────────────────┤
[서버]     조회 / 검사 ──────────────┤ ← 서버가 직접 측정
[네트워크] 응답 ─────────────────────┘
[에이전트] 브라우저로 릴리스
```

에이전트가 **시각**을 보내면 시계 스큐로 음수 지연이 나올 수 있다. **경과 시간**(단조 시계 기준)을
보내면 그 영향을 받지 않는다. 서버가 자기 구간을 더해 `hold_duration_ms`에 저장한다.

## 5. 분기

### 악성

```
S3 업로드 (SSE 암호화) → quarantine_files INSERT
download_events UPDATE → decision = BLOCKED
SSE 푸시               → 관리 콘솔 실시간 이벤트
Slack Webhook          → 알림
에이전트에 BLOCK 응답  → 에이전트가 브라우저에 403
```

S3 업로드와 Slack 전송 주체는 **API 서버**다 (아키텍처 리뷰 1.1 — 해시/캐시로 차단되는 건은 탐지
엔진을 거치지 않으므로, 엔진이 알림을 담당하면 가장 흔한 차단 경로의 알림이 빠진다).

> **⚠️ S3는 검사 대기실이 아니다.** 검사할 파일은 ⑤에서 **API 서버로 직접** 업로드된다(gRPC
> 스트리밍). S3에는 **판정이 끝난 뒤 악성인 것만** 올라간다.
>
> 미확인 파일을 전부 S3에 넣으면 ① 정상 파일이 쌓여 비용이 계속 늘고, ② 사용자가 받은 파일들이
> 클라우드에 모여 프라이버시 문제가 되고, ③ 격리 목록에 정상 파일이 섞여 쓸 수 없게 된다.
>
> 아키텍처 리뷰 2.2의 다이어그램 수정 항목("S3 화살표에 **악성 판정 시** 표기 — 지금은 미확인 파일
> 전부가 S3에 쌓이는 것처럼 보임")이 바로 이 오해를 막기 위한 것이다. 실제로 이 혼동이 발생했으므로
> 반드시 반영할 것.

### 안전

```
download_events UPDATE → decision = RELEASED
에이전트에 RELEASE 응답 → 붙잡고 있던 응답을 브라우저로 흘려보냄
```

**파일을 서버가 브라우저에 주는 것이 아니다.** 보류를 풀어줄 뿐이고, 최종 저장은 브라우저가 한다.
파일은 디스크에 두 번 기록된다 — 프록시 스풀에 한 번, 브라우저 임시 파일로 한 번.

**업로드받은 파일은 서버에서 삭제한다.** 안전 판정된 파일을 서버가 계속 들고 있을 이유가 없다.
S3에 남는 것은 악성 판정된 것뿐이다.

### 서버 장애

```
에이전트가 응답을 못 받음
  → 재시도/서킷브레이커/캐시 조회 없이 즉시 차단 (fail-close 고정)
  → decision = FAIL_CLOSE
```

초기 단계에는 서킷 브레이커와 로컬 캐시 폴백을 구성하지 않는다 (2026-09-15 결정).

**중요**: 이 경우 판정이 없으므로 `file_verdicts`에 행이 생기지 않는다. 즉 **"검사하지 못한 채
사용자에게 내보낸 파일"의 기록은 `download_events`에만 남는다.** 보안 사고 조사 시 가장 먼저 봐야
하는 목록이다.

## 6. 상태 컬럼 두 개의 역할 분리

`download_events`에 상태가 두 개 있는 이유다. 초안 ERD에서 `status`와 `verdict`가 "이중 진실"이었던
것을 고친 부분이다.

| 컬럼 | 뜻 | 값 |
|---|---|---|
| `pipeline_status` | **어디까지 갔나** (진행) | HELD → HASHED → LOOKUP → UPLOADED → ANALYZING → COMPLETED / FAILED |
| `decision` | **어떻게 됐나** (결말) | RELEASED / BLOCKED / BYPASSED / FAIL_CLOSE |

그리고 `verdict`(판정)와 `decision`(처분)도 다르다:

| | 판정 `verdict` | 처분 `decision` |
|---|---|---|
| 누가 | 검사 서버 | 에이전트 |
| 무엇 | 이 파일이 악성인가 | 브라우저에 뭘 돌려줬나 |
| 테이블 | `file_verdicts` `analyses` | `download_events` |

**서버가 죽으면 판정은 없는데 처분은 있어야 한다.** 그게 `FAIL_CLOSE`다.

`BLOCKED`(판정으로 차단)와 `FAIL_CLOSE`(검사를 못 해서 차단)는 **반드시 구분돼야 한다** — 장애
구간에 사용자가 받지 못한 파일 목록이 필요하고, 그중 정상 파일이 얼마나 막혔는지가 fail-close
고정의 실제 비용이기 때문이다.

## 7. 판정 무효화 흐름

### 오탐 복원

```
관리자가 격리 파일 복원
  → quarantine_files.status = 'RESTORED', restored_by/restored_at 기록
  → hash_whitelist INSERT (origin_quarantine_id로 출처 연결)
  → file_verdicts.is_stale = TRUE
  → Redis 해시 캐시 직접 삭제 (에이전트는 판정을 캐시하지 않아 통지 불필요)
  → audit_logs INSERT
```

`is_stale`과 `hash_whitelist`가 **둘 다** 필요하다. `is_stale`은 RDS 캐시를 무효화하고,
화이트리스트는 **블룸 필터가 여전히 양성으로 답하는 것**을 앞단에서 막는다.

### 룰셋 갱신

```
새 룰셋 활성화 (yara_rulesets.is_active 전환)
  → UPDATE file_verdicts SET is_stale = TRUE WHERE rulesets_version < <새 버전>
  → Redis 블룸 필터·해시 캐시 직접 삭제
  → 같은 해시가 다시 들어오면 캐시 미스로 재검사 → analyses 행이 하나 더 쌓임
```

"안전" 판정의 의미가 **"내가 가진 룰 전부와 대조했는데 안 걸렸다"**이므로, 룰셋이 바뀌면 이전 "안전"
판정은 보장되지 않는다. 그래서 판정마다 `rulesets_version`을 박아둔다.

## 8. MVP(4일)에서 실제로 도는 흐름

MVP는 블룸 필터·Redis·서킷브레이커·PE 엔트로피·관리 콘솔을 제외했다. 위 흐름 중 실제로 구현되는
부분만 남기면:

```
④ 보류 + 스풀 + 해시
⑤ 해시 조회 → hash_blacklist (RDS 직접 조회, Redis 없음)
            → file_verdicts (캐시 조회)
⑦ 캐시 미스 시 업로드
⑥ YARA 매칭만 (매직바이트·PE·엔트로피 제외)
⑨ 통과 / 403
```

- 조회 ①(화이트리스트) ③(블룸 필터)은 **MVP 밖** — 3주차 이후
- 격리는 S3 대신 로컬 폴더로 대체 가능
- `analyses` / `analysis_matches`는 `file_verdicts` 한 행으로 뭉개도 됨
- 필요한 테이블 4개: `agents` `download_events` `file_verdicts` `hash_blacklist`

## 9. 아직 결정하지 않은 것

### 9.1 캐시/블랙리스트로 차단한 건의 격리 파일

②나 ④에서 차단되면 **파일이 서버에 없다** (업로드를 안 했으므로). 그런데 격리는 파일이 있어야 한다.

| 방안 | 결과 |
|---|---|
| **격리 안 함** (권장) | 이미 아는 악성이라 샘플이 이미 있을 것. `download_events`에만 차단 기록 |
| 차단 시 업로드 요청 | 샘플은 모이지만, 아는 파일을 또 받느라 3단 파이프라인의 이점이 사라짐 |

스키마는 둘 다 지원한다 — `quarantine_files`가 `download_events`에 **선택적으로** 매달려 있어
"차단됐지만 격리 행이 없는" 상태가 정상이다.

### 9.2 `download_events` INSERT 시점

| 방안 | 트레이드오프 |
|---|---|
| 판정 후 한 번에 INSERT | 단순. 대신 판정 중 크래시난 건이 안 남고 `pipeline_status`가 항상 COMPLETED/FAILED로만 들어감 |
| 요청 시 INSERT → 판정 후 UPDATE | 미완료 건도 추적됨. 중간 단계 값에 의미가 생김 |

MVP는 전자로 가도 된다. 단 브라우저가 기다리는 중이므로 **INSERT가 판정을 지연시키지 않게** 해야
한다.

### 9.3 리스트 판정을 `file_verdicts`에 기록할지

`verdict_source`에 `WHITELIST` / `BLACKLIST` 값이 있으나, 리스트는 조회 사슬 ①②에서 걸러지므로
그 행들은 ④ 조회에 쓰이지 않는다. 기록하면 `hit_count`를 한 곳에서 집계할 수 있고 블룸 필터 재구축
쿼리가 어차피 UNION하므로 중복은 무해하다. **정하지 않으면 구현자마다 다르게 짠다.**

### 9.4 "N MB 초과 파일 정책"

⑤ 업로드 때문에 큰 파일이 문제가 된다. 브라우저는 **업로드가 끝나고 검사가 끝날 때까지** 계속
기다린다:

```
2GB 다운로드 → 2GB 업로드 → 검사 → 그제서야 브라우저가 저장 시작
```

가정·사무실 회선은 업로드가 다운로드보다 훨씬 느려서 체감 지연이 폭발한다. 처리할 컬럼은 이미 있다:

| 컬럼 | 용도 |
|---|---|
| `file_type_policies.max_inspect_size_bytes` | 이 크기를 넘으면 검사 포기 |
| `file_type_policies.oversize_action` | 그때 `PASS` / `BLOCK` / `WARN` 중 무엇을 할지 |

**한계값과 초과 시 동작이 아직 정해지지 않았다.** 아키텍처 리뷰의 1주차 리스크 3건 중 하나이며
(mitmproxy 스트리밍 모드에서 헤더가 언제 나가는지 실측 필요), 그 결과에 따라 정해야 한다.

## 10. 성능 지표를 뽑는 곳

제품 설계 10장의 측정 계획이 어느 컬럼에서 나오는지:

| 지표 | 소스 |
|---|---|
| p99 지연 | `download_events.hold_duration_ms` 분위수 |
| 캐시 히트율 | `download_events.cache_hit` 비율 (`decision_source`별 분해 가능) |
| 전송량 절감률 | `SUM(bytes_uploaded) / SUM(file_size)` |
| 검사 실패율 | `analyses.status <> 'SUCCESS'` 비율 |
| PC 현황 | `agents.last_heartbeat_at > now() - interval '3 minutes'` |

`cache_hit` `bytes_uploaded` `hold_duration_ms` 세 컬럼은 **업무 로직에 쓰이지 않는다.** 오직 이
측정을 위해 존재한다.

## 11. 검사 단계(⑤~⑥)의 위험과 4겹 방어

이 시스템에서 **가장 위험한 연산**이 ⑥의 파일 파싱이다. 흐름을 이해할 때 이 부분이 왜 이렇게
복잡하게 격리돼 있는지 알아야 한다.

### 위험의 정체 — 감염이 아니라 파서 취약점

파일이 디스크에 있거나 바이트를 읽는 것만으로 코드가 실행되지는 않는다. 실제 위험은:

```
조작된 파일 → 파서가 해석 → 파서의 버그를 건드림 → 파서 프로세스 안에서 공격자 코드 실행
```

즉 **"파일을 뜯어보는 프로그램" 자체가 공격 대상**이 된다. 제품 설계 7장의 사례들:

| CVE | 내용 |
|---|---|
| **CVE-2017-0290** | **Windows Defender가 파일을 스캔하는 것만으로 SYSTEM 권한 RCE** |
| CVE-2010-2568 | 탐색기가 `.LNK` 아이콘을 렌더링하며 코드 실행 (Stuxnet) |
| CVE-2017-11421 | 파일명에 담긴 VBScript가 썸네일 생성 시 실행 |

첫 줄이 핵심이다 — **검사하는 쪽이 최고 권한으로 뚫린 사례**이고, 우리가 만드는 것이 그 부류의
프로그램이다. YARA도 예외가 아니다(libyara 취약점 이력, 특히 PE 파싱 모듈). PE 헤더 파싱은
**공격자가 정한 숫자를 믿고 메모리를 읽는** 연산이라 YARA 문자열 매칭보다 더 위험하다.

### 4겹 방어

| 겹 | 조치 | 막는 것 |
|---|---|---|
| 1 | **사용자 PC에는 파서를 두지 않음** — 에이전트는 해시만 계산 | 단말 침해. CLAUDE.md 규칙: *"Do not add file-format parsing to the proxy/agent side"* |
| 2 | **탐지 엔진 컨테이너를 `internal: true` 네트워크에 격리** | 뚫려도 인터넷·AWS 메타데이터·Slack Webhook·IAM에 접근 불가 → 데이터 유출 통로가 없음 |
| 3 | **프로세스 분리 + 메모리·CPU·시간 상한** | 크래시 시 해당 파일만 실패 (`analyses.status` = `CRASH`/`OOM`/`TIMEOUT`이 이 때문에 있음) |
| 4 | **스풀 파일 무해화** (`UUID.tmp`, `0600`, XOR 인코딩, 인덱싱 제외) | 사용자 PC의 자동 파서(인덱서·썸네일러·백신)가 대기 중 파일을 건드리는 것 |

2겹이 Slack 알림과 S3 업로드 주체를 **탐지 엔진이 아니라 API 서버**로 옮긴 이유이기도 하다
(아키텍처 리뷰 1.1). 4겹의 XOR 인코딩은 스풀 파일의 매직바이트를 깨뜨려 **어떤 자동 파서도 "내
처리 대상"으로 인식하지 않게** 만든다.

3겹은 탐지 엔진 언어 선택과 직결된다 — Python은 `ProcessPoolExecutor` + `setrlimit`로 싸게 격리되나,
Java는 조작된 PE 하나가 JVM 전체를 죽여 검사 중인 다른 요청까지 실패한다 (아키텍처 리뷰 5.2).

### 발표용 답변

> "검사하는 프로그램이 가장 위험합니다. Windows Defender도 파일을 스캔하다 SYSTEM 권한을
> 내줬습니다. 그래서 위험한 파싱은 사용자 PC가 아니라 인터넷에서 격리된 서버 컨테이너에서만 하고,
> 거기서 크래시가 나도 해당 파일 하나만 실패하도록 설계했습니다."
